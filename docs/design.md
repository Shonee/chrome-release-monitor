# Release Radar for Chrome 设计文档

## 目标

项目由单一维护者管理。核心链路是可靠发现 Chrome Stable 版本变化，生成来源明确的双语静态文章，在推送远程仓库前完成构建验证，并通过独立工作流部署 GitHub Pages。

## 架构

- Astro 静态站点：Markdown 是页面、Feed、搜索和导出的唯一内容来源。
- 版本级文章：每个新完整版本生成独立文件，避免自动化覆盖人工整理的里程碑文章。
- 双数据源：Chromium Dashboard 为主源，Chrome Version History API 为回退源。
- 有限重试：超时、网络错误、429 和 5xx 使用指数退避；两个版本源均失败才终止。
- 内容降级：Release Notes enrichment 失败时仍生成版本事实文章，不阻塞核心发布。
- 推送门禁：采集结果必须通过测试、Astro 检查和生产构建才能提交。
- 独立部署：监控工作流在推送后调用可复用的 Pages 工作流；人工推送默认分支也可触发部署。

## 数据边界

- 自动文章只陈述官方 API 返回的版本、平台和时间。
- Version History API 不提供发布时间时，页面明确使用检测日期，不伪装为官方发布时间。
- 功能标题来自 Chrome Release Notes，安全修复数量和 CVE 只引用 Chrome Releases 官方公告。
- 下载页中的第三方入口不代表 Google 官方背书。

## 故障行为

- 没有数据变化：任务成功结束，不构建、不提交、不部署。
- Release Notes 不可用：记录 warning，生成无功能标题的保守文章。
- 单个平台主源失败：重试后切换备用源。
- 任一平台的主备版本源都失败：不改状态、不推送，保留上一次线上版本。
- 检查或构建失败：不提交、不推送、不部署。
- 推送冲突或权限不足：禁止 force push，任务失败并保留远端历史。

## 成功标准

- 错峰平台更新不会丢失。
- 重复运行对同一状态不产生新提交。
- 自动生成的中英文文章均通过 Content Collection 校验。
- 部署的提交与推送前验证的提交 SHA 一致。
